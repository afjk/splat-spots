# Splat Spots 方針

ChatGPT Sites 上の暫定公開から、GitHub Pages（フロント）＋ Cloudflare（API/DB）へ
移行するにあたって決めた方針。実装の判断に迷ったらここに戻る。

## 1. このサイトは何か

Insta360 Spatial Capture の**非公式・軽量な公開ギャラリー**。

- Insta360 公式ビューアは WebXR に対応していない。
  [`afjk/insta360-sog-xr-viewer`](https://github.com/afjk/insta360-sog-xr-viewer)
  がそれを埋める。Splat Spots は**そのビューアへの入口を一箇所に集める**役割。
- 現状、公開キャプチャは個別ページとして散逸的に共有されるだけで、
  まとまった一覧が存在しない。そこを埋める。
- **公式が埋めない隙間を埋め続ける。** 公式ビューアが WebXR に対応していないこと、
  公開キャプチャを横断して見られる場所が存在しないこと。この2つの欠落が存在理由であり、
  公式が何を出したとしても、埋まらない隙間は残る。**撤退の期限は設けない。**
  サイト上でも「いずれ不要になるもの」という書き方はしない。

### 名称

- **サイト名: Splat Spots**
- **タグライン: Unofficial gallery of Insta360 Spatial Captures**

タグラインは3つの仕事を同時にこなす必要があり、この一行で足りている。

| 要素 | 役割 |
|---|---|
| `Unofficial` | 公式を騙らない。先頭に置くことで誤解の余地を残さない |
| `Insta360 Spatial Captures` | 検索語として必要。互換性の説明としての商品名使用は問題ない |
| `gallery` | 視覚中心のサイトであることを宣言する（旧称の "atlas" と違い地図を約束しない） |

WebXR で見られることは公式ビューアとの最大の差分だが、タグラインには入れない。
ヒーローの本文と各キャプチャページの導線で示す。

`splat-atlas` からの改称にあたって必要な作業:

- GitHub リポジトリ名を `splat-spots` へ変更
- `public/og.png` の作り直し
- 旧 ChatGPT Sites 版の告知文を新 URL に差し替え（Phase 4）

### 載せるもの / 載せないもの

| 載せる | 載せない |
|---|---|
| すでに一般公開された共有 URL とそのメタ情報 | 非公開・限定公開のキャプチャ |
| Insta360 が生成した派生サムネイル（静止画＋低解像度ループ） | `.sog` / `.ply` / cameras.json などの 3D アセット本体 |
| 撮影日・カメラ機種・タグ・出典投稿 | 署名付きアセット URL の永続保存 |

- **3D アセットはミラーしない。** 閲覧時に公開元から直接読み込む。
- **派生サムネイルのみ保持する。** 削除依頼を受けたら索引ごと消す。
- ID 総当たりやクロールによる発見はしない。人が見つけた公開 URL の登録のみ。

## 2. アーキテクチャ

```
GitHub Pages ── 公開サイト（Astro / 静的・キャプチャごとに実 HTML）
     ↑ build
GitHub Actions ── push 時 + 日次ビルド、ffmpeg でサムネ生成
     ↑ read
   git: data/captures/*.json ── 公開カタログの「正」
     ↑ 人のレビューを経て反映（自動 PR）
Cloudflare Worker ── 投稿・削除依頼の受け口 / 日次生存確認
     └ D1 ── 受付箱（未公開の投稿・依頼キュー）
```

### なぜ git が「正」なのか

- **透明性** — 非公式索引だからこそ、何を載せているかが全部見える
- **耐久性** — Cloudflare が使えなくなってもカタログは残り、サイトも生き続ける
  （ChatGPT Sites で今まさに直面している問題への回答）
- **モデレーション** — 投稿を PR レビューで通せる
- **監査証跡** — 削除依頼 → ファイル削除のコミットが記録として残る

D1 は「受付箱」に徹する。**D1 の内容がそのまま公開されることはない。**

### Worker の責務（これ以外はやらない）

Insta360 の detail API は **CORS ヘッダを返さない**ため、ブラウザから直接叩けない。
Worker が必要なのは本質的にこの一点に由来する。

1. `POST /api/submissions` — URL 正規化＋公開検証 → D1 キューへ
2. `POST /api/reports` — 修正・削除依頼 → D1 へ
3. `GET /api/queue` — Bearer 認証。取り込み時に読む
4. Cron（日次）— 全件の公開状態を確認し、変化があれば通知（未実装 / Phase 3）

CORS は既知のオリジンだけをエコーする（任意のオリジンを反射しない）。
投稿フォームにはハニーポット項目があり、埋まっていた場合は保存せず成功を返す。

### 「存在しない」と「確認できない」を必ず区別する

Insta360 は存在しない ID に対して **HTTP 200 と `{"code":40004,"msg":"FindNotFound"}`**
を返す。HTTP のステータスだけを見ると成功に見えるため、本文を読む必要がある。

この区別は UX と安全性の両方に効く。

| 状態 | 意味 | 振る舞い |
|---|---|---|
| `not_found` | Insta360 が答えたうえで「知らない」 | 投稿を 404 で拒否。検証では `unavailable` に倒す |
| `unreachable` | 応答が得られない（ネットワーク等） | 投稿は 503。**検証では絶対に掲載を落とさない** |

一時的な障害で誰かの掲載が消えてはならない。逆に、打ち間違いに対して
「時間をおいて試してください」と言い続けてもいけない。

ビルド時のサムネ生成は Actions ランナーから Insta360 API を直接叩く（CORS 無関係）。
つまり **Worker はビルドの依存にならない。Worker が落ちてもサイトは出る。**

## 3. データ

`data/captures/<GS3DG…>.json` を 1 キャプチャ 1 ファイルで持つ。
現行スキーマ（`lib/captures/types.ts`）を踏襲しつつ、API から取れる情報を足す。

```jsonc
{
  "id": "GS3DG…",
  "insta360_url": "https://app.insta360.com/3dspace/detail/GS3DG…",
  "title": "…",
  "description": "",
  "captured_at": "2026-08-14",   // API の titleDate
  "camera": "X4 Air",            // API の cameraType
  "source_post_url": null,
  "source_author": null,
  "discovered_at": "2026-08-23T00:00:00.000Z",
  "last_checked_at": "…",
  "status": "available",         // available | unavailable
  "tags": []
}
```

`lib/captures/normalize.ts` と `lib/verification/insta360.ts` は
**そのまま移植する**。URL 正規化と公開検証のロジックは既に正しい。

## 4. サムネイルのパイプライン

detail API は Insta360 が自動生成した周回動画 `4_effect_1.mp4` を返す。
ただし **14MB / 7 日間の署名付き / 未署名は 403**。そのままは使えない。

実測で分かった、この素材の性質（`scripts/build-thumbs.mts` はこれを前提にしている）:

| 性質 | 影響 |
|---|---|
| **H.265 (HEVC Main 10)** | ブラウザの HEVC 対応はばらつく。H.264 への変換が必須 |
| **1080×1920 の縦型** | カードは 4:5 縦型。切り出しはエンコード時に行う |
| **14.03秒の固定テンプレート** | 前半は粒子が集まる演出で、**実シーンが現れるのは末尾の2〜3秒だけ** |

最後の点が重要で、先頭付近のフレームを取ると抽象的なノイズ画像になる。
静止画も動画も**末尾から**サンプルする。解決済みのシーンは高周波成分が少なく、
結果としてファイルも桁違いに小さくなる。

ただし**カメラの最終位置は制御できない**。末尾付近の複数フレームを試して
最も情報量の多いものを選ぶが、クリップ全体が壁で終わっている場合は
どう選んでも良い絵にならない。その場合は `--at` で秒数を指定する。
（同じキャプチャの2本目の effect 動画も試したが、カメラパスが違うだけで
末尾が壁になる傾向は同じで、ダウンロード量が倍になるだけだった。）

```
detail API → effect mp4 (14MB, HEVC, 縦) → ffmpeg（末尾から / H.264へ）
        ├ public/thumbs/<id>/poster.jpg   720x900   実測 27–54KB
        ├ public/thumbs/<id>/og.jpg       1200x630  実測 34–49KB
        └ public/thumbs/<id>/loop.mp4     480x600   実測 49–71KB
```

- 画像は **webp ではなく mjpeg**。webp エンコーダを持たない ffmpeg ビルドが実在するため、
  CI とローカルで結果が食い違わないほうを取る
- **サムネイルはコミットしない。**`public/thumbs/` はビルド成果物で、gitignore する
- **すでに存在するなら再生成しない。**`--force` で明示的に上書き
- 生成に失敗したキャプチャは、プレースホルダを出しつつ索引には残す

### 削除は完全でなければならない

「掲載を止めました」と言ったあとに、その画像がどこかから取得できてはいけない。
サムネイルをコミットしていると **git 履歴に永久に残り、全クローンに複製される**。
これは撮影者への約束と両立しない。

したがって `public/thumbs/` は git に入れず、`npm run thumbs` が毎回
`data/captures/` と照合する。レコードのないサムネイルは削除される。

| 置き場所 | 削除の確実性 | 採否 |
|---|---|---|
| git にコミット | 履歴に残り続ける | **不可** |
| ビルド時に生成（現行） | レコードを消せば次のビルドで消滅。掃除し忘れる場所がない | **採用** |
| R2 に保存 | 実際に消えるが、**消す場所が2箇所**になり片方を忘れうる | 見送り |

R2 を採らないのは、`npm run remove` で潰したのと同じ「手順の片側だけ実行される」
失敗をまた作るため。件数が増えてビルド時間が問題になったら再検討する。

削除依頼への対応は `npm run remove` にまとめてある。

## 5. デザインの方向

現状の「ダサさ」の主因は配色ではなく、**ギャラリーなのに画像が一枚もない**こと
（`components/capture-card.tsx` は CSS で疑似 splat を描いている）。まずそこを直す。

- **ダークキャンバス固定** — `#0a0a0b` 系。splat は暗背景で最も映える
  （Polycam / Luma / Sketchfab はいずれもこの選択）。ライトテーマは用意しない
- **動画ファーストのグリッド** — poster を表示し、ホバー／画面内進入で `loop.mp4` を再生。
  縦横比は統一（masonry より整然としたほうが 3D キャプチャは映える）
- **カードのメタ** — タイトル / 撮影日 / カメラ機種 / 作者 / タグ / XR バッジ
- **詳細ページ** — ビューアを全幅で上に置き、メタ情報は下のレール。
  「Enter VR」を最大の導線にする
- **継承するもの** — mono 系のアクセント（技術的アーカイブという性格に合う）
- **捨てるもの** — 紙色 `#f2f0e9` ＋アシッドグリーンの組み合わせ、疑似 splat 表現、
  および位置情報を持たないのに地図を匂わせるヒーローの座標装飾（`35.6762° N` 等）

キャプチャごとに実 HTML を生成するので、**個別の OGP 画像が出る**。
散逸的に共有されている現状を一箇所に集める、という意図にこれが直接効く。

## 6. 移行の段取り

| Phase | 内容 | 完了条件 |
|---|---|---|
| 0 | ~~現 D1 と seed カタログを `data/captures/*.json` へ書き出す~~ **完了**（内容は方針変更により破棄し、カタログは空から再出発） | カタログが git にある |
| 1 | Astro 静的サイト＋サムネ生成＋GitHub Pages 公開 **（ローカルまで完了 / Pages 有効化待ち）** | **ChatGPT Sites に依存しない状態になる** |
| 2 | 自分の Cloudflare アカウントに Worker + D1 を立て、投稿／依頼フォームを接続 **（実装・ローカル検証まで完了 / デプロイ待ち）** | 投稿を受け付けられる |
| 3 | Cron 生存確認と、キュー取り込みの自動 PR | 運用が回る |
| 4 | ChatGPT Sites 版を停止し、移転を案内 | 移行完了 |

Phase 1 の完了時点で当初の懸念（将来使えなくなる）が解消される。ここを最優先。

## 7. 公開先

- サイト: `https://afjk.github.io/splat-spots`
- ビューア: `https://afjk.github.io/insta360-sog-xr-viewer/?id=GS3DG…`（同一オリジン）
- API: Cloudflare Workers（`*.workers.dev` で開始）

独自ドメインは採らない。将来移す場合に備え、ビューア URL の組み立ては
`lib/viewer/adapter.ts` の 1 箇所に閉じ込めたまま維持する。

## 8. 引き続きスコープ外

- 広域クロールや ID 列挙による発見
- `.sog` / `.ply` の永続ミラー
- 所有者確認を伴う本格的なモデレーション基盤
- ユーザーアカウント、コメント、いいね
