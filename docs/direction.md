# Splat Spots 方針

有志が公開 Spatial Capture のリンクを持ち寄る、非公式のディレクトリ。
実装の判断に迷ったらここに戻る。

## 1. このサイトは何か

- **サイト名: Splat Spots**
- **タグライン: Community-curated directory of publicly shared Insta360
  Spatial Captures. Unofficial and not affiliated with Insta360.**

公式ビューアが WebXR に対応していないこと、公開キャプチャを横断して眺められる場所が
存在しないこと。この2つの欠落が存在理由であり、公式が何を出したとしても、
埋まらない隙間は残る。**撤退の期限は設けない。**
サイト上でも「いずれ不要になるもの」という書き方はしない。

ビューア本体は
[`afjk/insta360-sog-xr-viewer`](https://github.com/afjk/insta360-sog-xr-viewer)。
Splat Spots は**そのビューアへの入口を一箇所に集める**役割。

## 2. 原則

この節が他のすべてに優先する。

1. **Splat Spots は Spatial Capture のホストにならない**
2. **`.sog` / `.ply` / 動画を保存・再配布しない。Insta360 由来の画像も持たない**
   （投稿者が自分でアップロードしたサムネイルだけは持つ。3 を見よ）
3. **Insta360 の内部 API を自動利用しない**
4. **Insta360 のサイトを crawler / bot 的に自動取得しない**
5. **公開 Capture の URL はユーザーが投稿する**
6. **投稿は即時公開する。掲載前の人手の確認は挟まない**
7. **撮影者・権利者からの削除依頼に速やかに応じる**
8. **Insta360 公式サービスと誤認されない表示にする**

### なぜ事前確認をやめたか

以前は投稿を D1 のキューに溜め、管理者が URL を開いて確認してから
`data/captures/` にコミットしていた。前提が壊れない代わりに、**掲載は管理者が
手を動かすまで進まなかった。**持ち寄る場所として、そこが一番の摩擦だった。

いま置いているのは、事前ではなく事後の防御である。

- URL の形式と hostname の検証（Spatial Capture の共有リンク以外は入らない）
- ハニーポットと、1時間あたりの投稿数の上限（IP はハッシュ化して数えるだけ）
- 削除依頼への即応。掲載を外すのは 1 行の UPDATE
- 投稿者が入れた文字列は**必ずテキストとして描画する**（`textContent` のみ）
- サムネイルは画像であることをバイト列で確かめ、`nosniff` を付けて返す

**明らかに不適切なものが一時的に載りうることは、この方針が受け入れた代償である。**
サムネイルを受け付けるようになった分、その代償は文字列だけだった頃より大きい。
その代わり、外すのは速い。

### なぜ内部 API をやめたか

かつては Insta360 の `gs3d/task/detail` を叩いて、公開状態の確認、タイトル・撮影日・
カメラ機種の取得、プレビュー動画の取得を自動で行っていた。技術的には動いたが、
**非公開・非公式のエンドポイントに依存し続けることは、運用の前提にできない。**
先方の都合でいつでも壊れるうえ、bot として他人のサービスを叩き続ける形になる。

代わりに置いたのは**URL の形式だけを見る検証**である。実際に公開されているか、
本当に Spatial Capture かは、Splat Spots には確かめる手段がない。
**開いてみるまで分からない**ことは、そのまま受け入れる。リンク切れの報告は
`POST /api/reports` で受ける。

将来、公式に利用可能な API が提供されたら再検討する。

## 3. 何を持ち、何を持たないか

| 持つ | 持たない |
|---|---|
| 公開共有リンクとその ID | `.sog` / `.ply` / cameras.json |
| 人が入力したタイトル・タグ・撮影者・出典 | Insta360 由来の画像・動画・その派生物 |
| このサイトが生成したカードのアートワーク | 署名付きアセットURL |
| **投稿者がアップロードしたサムネイル** | Insta360 から取得した thumbnail |

サムネイルが無い Capture のカードには、ID から決定的に生成した点群パターンが出る。
**サイトが自分で描いたもの**であり、Insta360 のコンテンツは一切含まない。
サムネイルは常にその上に重なるだけなので、**画像が落ちてもカードは崩れない。**

### サムネイルの置き場所

**画像は git に入れない。D1 にだけ置く。**
一度コミットした画像は履歴に残り続けるので、「消しました」が嘘になる。
D1 の 1 行が絵のすべてであり、行を消すことが削除のすべてである。

D1 が消えればサムネイルも消える。カードは生成アートワークに戻るだけで、
**カタログは壊れない。**この割り切りがあるから、画像を持つことを許せる。

- ブラウザ側で 4:3・最大 1200×900 の JPEG に焼き直してから送る
  （縮小・EXIF の除去・アップロードサイズの抑制が一度に済む）
- Worker は宣言された MIME と実バイトの先頭が一致することだけ確かめる。
  **画像をデコードしない**
- URL に version を持たせて長期キャッシュする（差し替えれば別 URL になる）

これは「投稿者本人による画像アップロードが使えるようになったら再検討する」と
書いていた箇所そのものである。Insta360 由来の画像を持たない点は変わっていない。

## 4. アーキテクチャ

カタログは2つに割れている。

```
GitHub Pages ── 公開サイト（Astro / 静的）
     ↑ build                    │ 読み込み後に fetch
GitHub Actions                  ↓
     ↑ read              Cloudflare Worker ── 投稿・削除依頼の受け口
   git: data/captures/*.json         └ D1 ── ライブなカタログ
     ↑ 管理者が手で追加
```

- **git の半分** — 管理者がコミットした分。ビルド時に実 HTML になる
- **D1 の半分** — 投稿された分。ギャラリーが読み込み後に取得して足す

**同じ id が両方にあれば git が勝つ。**ライブの行を後から
`data/captures/` に落としても、URL も見た目も変わらない。

ビルド後に追加されたスポットには静的な `/s/<id>` が存在しないので、
`404.astro` が同じ URL でその場に描く。**あとでコミットしてもリンクは切れない。**

### なぜ git を残すのか

- **透明性** — 非公式索引だからこそ、何を載せているかが全部見える
- **耐久性** — Cloudflare が消えてもコミット済みのカタログとサイトは生き続ける
- **監査証跡** — 削除依頼 → ファイル削除のコミットが記録として残る

D1 が消えればライブの半分は消える。**それは受け入れる。**
残したいものはコミットする。

### Worker の責務（これ以外はやらない）

1. URL を parse する
2. 許可された hostname か確認する
3. Spatial Capture URL の形式か確認する
4. Capture ID を抽出する
5. 重複投稿を集約する（1 capture 1 行）
6. D1 に掲載として保存する
7. `GET /api/captures` でライブなカタログを返す

**Insta360 への通信は行わない。** `POST /api/reports` と、Bearer 認証付きの
`GET /api/queue`（入ってきたものと未処理の依頼）も持つ。

CORS は既知のオリジンだけをエコーする（任意のオリジンを反射しない）。
フォームにはハニーポット項目があり、埋まっていた場合は保存せず成功を返す。
投稿と依頼には1時間あたりの上限があり、生の IP ではなくそのハッシュで数える。

## 5. データ

`data/captures/<id>.json` を 1 キャプチャ 1 ファイルで持つ。

```jsonc
{
  "id": "GS3DG…",
  "url": "https://app.insta360.com/3dspace/detail/GS3DG…",
  "title": "Example Spot",
  "description": "",
  "author": null,
  "tags": ["architecture"],
  "source_post": null,
  "camera": null,        // 確実に分かる場合のみ
  "captured_at": null,   // 確実に分かる場合のみ
  "submitted_at": "2026-08-23",
  "status": "published"  // published | unlisted
}
```

**API 由来でしか取れなかった項目を必須にしない。** `camera` と `captured_at` は、
ユーザー入力か管理者が確実に知っている場合だけ設定する。推測で埋めない。

`status` は残してあるが、git 側でいま自動で書き換えるものは存在しない。
D1 側の `status` は掲載の可否そのもので、`published` か `removed` を取る。

## 6. 掲載の流れ

```
フォーム → 形式の検証 → D1 → その場でギャラリーに並ぶ
                              ↓ 残したいものだけ
                      data/captures/<id>.json
```

**投稿された瞬間に公開される。**確認は事前ではなく事後に行う。

投稿は誰でもできる。自分が撮ったものでなくてよい。ただし
**すでに一般公開されているもの**に限る、とフォームに明記する。

管理者がすることは、入ってきたものを眺めることと、外すべきものを外すこと。
残したいものは `npm run add` で git に落とす。

## 7. 削除

**掲載は2箇所から来るので、外すのも2箇所**である。`npm run remove` は
git のファイルを消し、D1 側の2文を必ず出力する。

```
UPDATE submissions SET status='removed' WHERE capture_id='GS3DG…';
DELETE   FROM thumbnails WHERE capture_id='GS3DG…'
```

`removed` にした id は、**再投稿されても戻らない。**
サムネイルは持っているのがバイト列そのものなので、隠すのではなく消す。

かつてサムネイルを git に置いていた頃は、削除しても履歴に画像が残った。
**D1 にしか置かないのは、この問題を二度と作らないためである。**

## 8. デザインの方向

- **ダークキャンバス固定** — `#08080a` 系。ライトテーマは用意しない
- **カードはサムネイル、無ければ生成アートワーク** — 後者は Capture ID から
  決定的に描くので、同じ Capture は毎回同じ絵
- **サムネイルは投稿時にブラウザで 4:3 に整える** — 縦長でもパノラマでも、
  切り落とさず全体を入れ、余白は自分自身をぼかしたもので埋める
- **カードのメタ** — タイトル / 説明 / 撮影者 / タグ、分かる場合のみ撮影日・カメラ
- **詳細ページ** — ビューアを全幅で上に置き、メタ情報は下のレール
- **継承するもの** — mono 系のアクセント（技術的アーカイブという性格に合う）

コミット済みのキャプチャは実 HTML になる。ライブの分は `404.astro` が
同じ URL でその場に描くので、リンクとしては同じように扱える。
**個別の OGP 画像は持たない**（画像を生成・保持しない方針のため）。
共有時はサイト共通の OG 画像になる。

## 9. 公開先

- サイト: `https://afjk.github.io/splat-spots`
- ビューア: `https://afjk.github.io/insta360-sog-xr-viewer/?id=GS3DG…`
- API: `https://splat-spots-api.afjk01.workers.dev`

ビューア URL の組み立ては `src/lib/viewer.ts` の 1 箇所に閉じ込めておく。

## 10. 経緯

このサイトは ChatGPT Sites 上の Next.js アプリとして始まり、次の順で移した。

| | 移したもの | 状態 |
|---|---|---|
| 1 | フロントエンドを Astro + GitHub Pages へ | 完了 |
| 2 | 受付を自分の Cloudflare アカウントの Worker + D1 へ | 完了 |
| 3 | 旧 Next.js 実装の撤去 | 完了 |
| 4 | ChatGPT Sites 版の停止 | 完了（2026-08-23） |
| 5 | Insta360 内部 API への依存の除去 | 完了（2026-08-23） |
| 6 | 事前レビューをやめ、投稿を即時公開に | 完了（2026-08-24） |
| 7 | 投稿者によるサムネイルのアップロード | 完了（2026-08-24） |

移行の動機は2つあった。**見た目**と、**基盤がいつまで使えるか分からないこと**。
後者は「特定の事業者に預けたものは、その事業者の都合で消える」という一般の問題で、
5 の判断（他人の非公開 API に依存し続けない）も同じ理由から来ている。

いま依存しているのは GitHub Pages と Cloudflare Workers + D1。
6 でライブな半分を D1 に置いたので、**D1 が消えればその分は消える。**
残したいものは `data/captures/` にコミットする。そちらは git にある限り残る。

## 11. スコープ外

- 広域クロールや ID 列挙による発見
- Capture 本体や派生画像の保持
- Insta360 由来の画像・動画の取得と保持
- Insta360 の内部 API を用いた自動確認・自動 verify
- 所有者確認を伴う本格的なモデレーション基盤
- 掲載前の人手による確認（6 で外した。事後の削除で受ける）
- ユーザーアカウント、コメント、いいね
- XR Viewer 側の仕様変更（別リポジトリ・別課題）
